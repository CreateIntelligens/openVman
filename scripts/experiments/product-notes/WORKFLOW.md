# 產品資料與問答驗收流程

這份流程用於之後收到新型錄、補規格或修改選型程式時，保存可比較的測試證據。每批資料與回答獨立封存，結論持續更新同一份 [REPORT.md](REPORT.md)。

## 現在讀什麼資料

| 資料 | 現在的用途 | 更新時要核對 |
|---|---|---|
| `knowledge/products/*.md` 的 YAML frontmatter | `filter_products` 直接讀取的產品規格；正文保留說明與來源 | 型號、數字、單位、缺值與原文出處 |
| `knowledge/products/_catalog.yaml` | 定義篩選欄位、型別與單位 | 欄位名稱與每篇產品筆記一致 |
| 既有 QA CSV，例如 `knowledge/qa/evak_qa.csv` | 原本的問答知識資料，供知識檢索使用 | 問答內容是否仍符合新型錄 |
| 型錄原文與一般知識文件 | 語意檢索與回答引用的依據 | 版本、頁碼、文件是否啟用 |

產品選型工具目前讀 **Markdown 的結構化欄位**，不直接拿 QA CSV 當產品規格表。兩條路徑並存。Obsidian 是可選的編輯器，服務不依賴它；規格更新後，QA 若仍寫舊數字仍可能讓回答矛盾，因此要一起核對。

供應商交來 PDF、Excel 或 CSV 時，先核對原文，再整理成上述產品筆記與 catalog。把來源檔放進資料夾不代表產品規格已自動更新。缺資料用缺值表示；額定工作點與獨立最大值分開，不能把最大揚程、最大流量視為同一工作點。

## 重核已封存的 117 款結果

在 repo 根目錄執行，需 Python 與 PyYAML：

```bash
python3 -B scripts/experiments/product-notes/acceptance/20261012_117/check_offline.py
```

這個入口依序檢查來源重建與防覆蓋、凍結題目、測量隔離、篩選工具回放、評分輸入與 60 份回答的完整性。缺少的筆記、評分輸入與 summary 會從上版證據重建；若本機副本被改過則停止。預設不修改報告。需要重建同一份報告時加 `--update-report`。

通過表示證據對得起來，**不表示 60 份答案都正確**。這批實際為 28 對、26 部分對、6 錯。指令不連正式服務、不呼叫模型，也不驗證 HTTP、語音或部署狀態。

Git 的雜湊欄位例外另外有回歸檢查，需安裝 Gitleaks：

```bash
python3 -B scripts/experiments/product-notes/acceptance/20261012_117/test_manifest_secret_scan.py
```

根目錄 `.gitleaks.toml` 保留預設偵測規則，僅允許本批兩份回答檔中特定來源檔案的完整 SHA-256 行。測試確認同檔案的金鑰欄位，以及其他檔案的相同行仍會被偵測。

## 收到新資料或要重新測量

1. **收資料與核對。** 保存原型錄版本、來源頁碼與檔案雜湊，列出新增／修改／刪除的型號與欄位。逐項核對產品筆記、catalog、相關 QA 與原文，先在 dev 驗證，不直接覆蓋這批封存證據。
2. **建立新批次。** 在 `acceptance/<日期_批次>/` 保存新來源快照、程式版本與必要設定。核對正式／dev 的知識文件、啟用狀態及 metadata；差異要解釋並留證，不能把不一致改標為通過。若資料或程式版本不同，就不是舊批次的完全重現。
3. **先定題、再定標準答案。** 保留可比較的題目，增加新規格的邊界、缺值、排序、多條件與資料不存在題。根據原文獨立核對預期型號、必要資訊及禁止推論；確認後凍結題目、標準答案與來源雜湊，才開始讓模型回答。不要從模型答案反推標準答案。
4. **先試跑，再正式跑。** 前置試跑只查執行問題，不混入正式分數。正式測量每題跑 3 次，每次使用新 session，生成端不可看到標準答案；記錄實際模型、決策、工具參數／輸出與失敗。保存前後資料雜湊，確認未寫入正式／dev 的 workspace 或 LanceDB。
5. **每份新回答重新評分。** 逐份對照凍結標準與原文，保留對／部分對／錯的原因、漏項、錯誤陳述與引用位置。評分綁定本次回答與評分輸入雜湊，不能套用上次的評分，也不能只挑最好的一次。
6. **驗證與比較。** 重放工具運算，分清規格資料錯誤、條件解析錯誤、工具運算錯誤、回答漏款或推論錯誤。彙整三次結果與穩定答對題數；沿用題與新增題分開比較。獨立最大值誤當工作點、缺值誤當符合等錯誤，要列入是否適合上線的判斷。
7. **更新報告、保留證據。** 更新同一份 `REPORT.md` 的新批次節、README 與 CHANGELOG。Git 保存腳本、凍結題目、來源快照、原始回答、逐份評分及必要核對證據；可重建的副本與中途 checkpoint 不重複提交。部署後的 HTTP、前台與語音測試另外記錄。

## 現有腳本的適用範圍

`20261012_117` 是固定的歷史批次：來源、20 題、手算標準答案、檔案數與評分包都綁定這 117 款。新資料需建立並核對自己的批次腳本與驗證值，不能只複製目錄後換型錄，或把舊腳本的檢查關掉。

只想用相同資料再次呼叫模型，可使用該批 `run_acceptance.py --full --questions-sha256 <凍結題目雜湊> --run-label <新名稱>`。它另存新回答與 checkpoint；後續評分、工具稽核與彙整仍需明確指向新回答並重新核對，現有 `prepare_grading.py`／`verify_artifacts.py` 預設核對原本的 `results.json`，不會自動評分新名稱的結果。完整生成需要相容的服務與設定，LLM 的文字及分數不保證重跑相同。

離線核對則要求同一批證據可重建，並在來源、回答或評分被改動時失敗。這兩種測試的目的不同。
