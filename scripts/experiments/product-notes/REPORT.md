## 實驗方法

固定供應商 `gemini`、模型 `gemini-3.5-flash-lite`、temperature `0.3`，實際 45 個 LLM 回覆均為同一模型。固定單一 route，沒有模型備援。各組回答使用完全相同的系統提示與 3,000 token 上限，只換參考資料；條件解析上限 1,600 token。完整提示與原始回覆保存在腳本及 [results.json](results.json)。

- **A**：現行 `_search_tool("knowledge", {"queries": [q]})` 原樣結果，包括 `results`、`related` 與出處。本次各題都是 3 個 results、0 個 related。
- **B**：A 加最相近 3 篇生成筆記；筆記向量只在子程序記憶體中計算，與 `_search_one` 查詢向量使用同一模型、維度與 revision 的 document/query identity，以 cosine 排序。
- **C**：B 再加同一 LLM 把問題轉成的條件 JSON，以及腳本對全 5 篇 frontmatter 篩選的結果。白名單欄位／運算、AND、單欄排序；`matches/unknown/excluded` 分開，未知值不當成確認排除。

回答順序依題號循環 A/B/C、B/C/A、C/A/B；每次沒有對話歷史。未把標準答案提供給回答模型，也未呼叫正式 chat API。生成提示曾由人工先指出型錄缺少 HP／揚程／口徑，因此零數值錯誤是這個受約束生成方式的結果，不能當成任意型錄自主抽取皆可靠的證據。原始生成筆記未校正便參與 B/C，核對結果另存，不把修正後筆記混入測量。

評分依凍結的 `required_points` 與 `forbidden_claims`，由 Codex 主代理與獨立代理分題對照原文評分，沒有額外實驗 LLM 自評呼叫。頁次誤植及前後已釐清的措辭矛盾另列品質問題。例如 Q05-C 清單括號寫「10m 未超過 9m 限制」，後段明確說 9m≤10m；主集合與最終推理正確，判對並保留矛盾記錄。Q08-A 雖最後拒絕以代碼選型，仍說「80 通常可能是 80mm 約 3 吋」，命中事前禁止猜口徑的規則，判錯。

## 篩選工具的限制

C 沒有新增答對題數，條件 JSON 全 10 題都可解析，但可解析不等於語意完整：

- Q05 把 9m／11m 兩情境壓成 `max_depth_m >= 11`，只產出 11m 空集合；回答仍靠 A/B 補足。
- Q06 把工況深度不超過 10m 解讀為產品 `max_depth_m <= 10`；若表示支援 10m 工況，能力應為 `>= 10`。本批全是 10m，所以候選集合相同，仍不能認定方向處理正確。
- Q03 的說明含「H1 同值再依 H」，實際 JSON／腳本只有單欄排序；本題無同值，尚未暴露結果錯誤。

這些問題已另列在 `results.json.filter_audit`。目前只是子程序篩選模擬，未註冊工具到正式 Brain。

## 建議與不確定處

openVman 可優先繼續驗證 **B 的結構化產品筆記**：它在此批補足跨段落資訊並減少無來源數字，但必須先補完整出處、修正材質語意錯誤，且將缺值保留與原文核對做成入庫閘門。這次不建議直接導入正式知識庫。

先補齊來源的逐型號 HP／額定及最大揚程／口徑資料，再擴大到 EUB、HIPPO 等跨系列、不同問法及更大產品量。10 題來自同一份型錄且每題只跑一次；同樣分數不能證明 B/C 長期等效。未獨立比對原始 PDF，也未測正式人格、回答字數限制、工具自主選擇、語音或完整 agent loop，因此不能宣稱正式問答品質已改善。

C 應先修多情境表示、能力與需求的比較方向、多欄排序，以及工具 unknown 狀態的語意，再用預先凍結的新增題集測量它能否超過 B。這次所有 `related` 都是空陣列，亦不能用本實驗判斷圖譜擴充本身的效益。
