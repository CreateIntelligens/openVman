# Jev API 評估結果

日期：2026-09-22（Asia/Taipei）。範圍：離線合成案例；沒有接入正式流量。

## 結論

Jev 在同一份合成案例上 **96/96 全對**，正反序均 100%，**零翻轉**。
在 SemIf 報告中列為缺失證據的「官方 Jev API 結果」已補上。

> [!IMPORTANT]
> 這是 48 筆合成開發案例的結果，不是校準過的生產 KPI 或保留集。
> SemIf 報告中「先建立獨立保留集與順序穩定性驗收」的建議仍然成立。

## 解讀

1. **準確率**：Jev 消除了 SemIf 的所有錯題（routing 12 題、interrupt 3 題），同時也消除了 BGE-M3 的 5 個錯誤。
2. **順序穩定性**：SemIf 有 13–14/32 翻轉；Jev **0 翻轉**，完全消除順序敏感。
3. **延遲**：Jev p50 約 260 ms（含網路往返），比 SemIf 本機 GPU 推論（約 415 ms）更快；但比 BGE-M3 embedding（71 ms）慢約 3.6 倍。GuardAgent 規則是 in-process 呼叫（0.003 ms），不在同一比較基準。
4. **成本**：96 次呼叫的 token 用量由 SDK 記錄在 predictions.jsonl。實際費率**待查** — 本次沒有取得官方計費頁佐證，不要當成已確認的數字引用。

## 限制

- 這 48 筆是人工合成繁體中文，不是真實用戶抽樣，不能直接承諾正式準確率。
- 延遲含台灣→美西網路，生產部署若需更低延遲，需考慮 region 與批次。
- Jev 不生成文字，只做決策；需與生成式模型配合使用。
- 本次沒有測試 RAG 證據篩選、對話歷史保留、真實語音時序、端到端改善。

## 後續建議

1. ✅ Jev API 接入已驗證，結果明顯優於 SemIf 與 BGE-M3。
2. 下一步：建立獨立保留集（非開發集），確認泛化能力。
3. RAG 證據篩選是另一個新實驗，排在保留集之後。
4. 若延遲可接受（p50 ~260 ms），可考慮做正式分流的 Jev 適配器。

## 2026-09-23 補充：能取代哪些現有判斷

`eval_replacements.py` 用 `replacement_cases.jsonl`（自寫 70 題）加 SemIf fixture 的 16 題打斷案例，
同一題讓現行規則與 Jev 各判一次。逐題結果：`results/replacements.txt`。

| 判斷 | n | 現行做法 | Jev |
|---|---|---|---|
| save_memory 是否明確要求記憶（`memory_tools.py`） | 20 | regex 5/20 | 20/20 |
| prompt injection／越獄（`safety/guardrails.py`，4 條英文 regex） | 20 | 11/20 | 20/20 |
| 語音打斷 STOP／IGNORE（`backend/app/guard_agent.py`） | 30 | 23/30 | 29/30 |
| A2A 是否需要回覆（現在靠整輪 LLM 回 `[[A2A_NO_REPLY]]`） | 16 | — | 16/16 |

- 單題呼叫 p50 約 350 ms；四題放同一次呼叫 p50 也約 350 ms（p95 兩次分別 381／742 ms），
  所以每輪只需一次 Jev 呼叫就能同時拿路由、記憶、攻擊等判斷。平均輸入約 410 token。
- **偏差**：題目是自己寫的，刻意放了規則會誤判的句子，規則分數被壓低；只說明 Jev 能處理規則
  處理不了的類型，不代表正式流量準確率。打斷的原 16 題 fixture 兩邊都全對，差距全在新題。
- 不適合：PII 偵測（目的是不外送，改外部 API 違背目的）、影像事件、需要長文生成的抽取。
