# 每輪回應延遲：從講完到聽到聲音

狀態：Draft（2026-10-09）。使用者確認前維持 Draft。

## 現況

前台每輪記錄各時間點到 `backend/logs/turn_timing.jsonl`。2026-09-29～10-06 共 35 輪，正常播放的 19 輪：

| 情境 | Brain 回答 | TTS 第一段聲音 | 講完到聽到聲音 |
|---|---|---|---|
| 文字＋IndexTTS（9 輪） | p50 4.1 秒 | p50 3.4 秒 | p50 7.0 秒、p90 7.7 秒 |
| 文字＋Gemini TTS（6 輪） | p50 4.3 秒 | p50 2.2 秒 | p50 6.6 秒、p90 6.8 秒 |

Brain 這段（`usage.db`，近 4 天 112 輪）：每輪呼叫 LLM 2 次（96 輪）或 3 次（16 輪），每次 p50 1.3 秒、p90 1.8 秒，主對話模型 gemini-3.5-flash-lite。第一次只產生約 30 tokens，內容是呼叫 `search_knowledge`；查完第二次才寫回答。另外每輪決策原本固定 1.03 秒（見下）。

各段是串行的：決策 → LLM 第一次 → 檢索 → LLM 第二次 → 整段回答回到前台 → 才開始 TTS。

## 已完成

- **系統提示固定內容在前**：兩個不同問題的系統提示相同開頭 79% → 96%（正式鶴記），部署後量 `usage.db` 的 `cached_tokens` 比例。
- **每輪決策 1.03 秒 → 0.34～0.49 秒**（ee48547）：14 題約 2,000 tokens，Clef 960 ms，主備兩站在每站 0.4 秒都逾時，每輪由 Jev 回答。縮成 5 題、每站 0.6 秒後每輪由 Clef 回答；30 句標註訊息判錯 0 個欄位（原本 6 個）。後台決策供應鏈停用 `clef-backup`（CPU 那台單題約 4 秒）。

2. **需要知識庫時先查再叫 LLM**：每輪決策判定 `needs_knowledge=True`（高信心）時，直接用使用者原句（加上一輪上下文）先跑 `search_knowledge`，把結果放進第一次呼叫，省掉只為了叫工具的那一次 LLM（約 1.2 秒）。模型仍可追加查詢。風險：追問句（「那價格呢？」）用原句檢索會變差，要用鶴記 20 題驗收與盲測題組確認不退步；需要 `filter_products` 的選型題仍要模型組參數，這類題省不到。Live 模式已經有預先查詢。
3. ~~決策與其他準備工作並行~~：量過、不做。決策只要對「需不需要記憶」有把握（是或否）就跳過自動回憶，Clef 30 句只有 3 句沒把握，並行只會每輪多做一次用不到的檢索與 Jev 篩選；設定快取過期時重新抓取只要 7～11 ms（第一次建連線 240 ms）。

## 決策功能審查待辦（e9b49ee 等 4 個 commit）

- Live 預先查詢不送 `server_search_results`，判定需要知識庫的回合前台看不到引用與圖片（功能退化）。
- Live 決策還沒回來時停止錄音或改打字，`CancelledError` 沒接住，可能讓 relay 連線斷掉、這輪回答遺失。
- Live 預先查詢沒有總時限（上網查詢最多約 20 秒），使用者講完到模型開口之間全部串行等待；視覺事件也跑完整決策。
- `/api/v1/internal/decision-providers` 回傳所有決策金鑰明文，邊緣 nginx 沒擋 `/api/v1/internal/`，只靠 `GATEWAY_INTERNAL_TOKEN`（這個 token 也會送給外部 TTS 節點）。
- 只管一個專案的 admin 能改整站決策設定；repo 慣例跨專案設定限 ROOT。
- 插話判斷呼叫決策鏈時沒帶每站時限，第一站慢就用完 0.6 秒，Jev 輪不到，一律判 STOP。
- 判定需要知識庫／記憶時無視 `CHAT_FORCE_KNOWLEDGE_SEARCH`、`AUTO_RECALL_ENABLED`，與設計文件不符。
- 前台 Debug 按鈕蓋住「快速問題」按鈕上半部，非 kiosk 都看得到；樣式寫死 px 與顏色。
