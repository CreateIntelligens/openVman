# 產品規格篩選工具：讓選型問題答得出完整清單

狀態：Draft（2026-10-06）。使用者確認前維持 Draft。

進度（2026-10-07）：已部署（f223ca2）。工業示範專案（開發） 經 `/api/v1/chat` 20 題×3 次 45／11／4（部署前同路徑 5／5／10），見「工業示範專案（開發） 驗收」。正式工業示範專案已放入全型錄 117 款的規格表，見「正式工業示範專案」。

進度（2026-10-12）：117 款新題的固定程式快照驗收完成，20 題×3 次為 **28／26／6**，三次都完整答對 4/20 題。工具入口參數防護已補強，但仍有模型漏叫、條件過寬及回答漏款／改錯數字；不是最新程式或部署後 HTTP／語音驗收，不能把計畫標為 Done。見「117 款新題驗收」與同一份實驗報告。

## 為什麼要做

客戶問「3 吋口徑、揚程 20 米以上的有哪幾款」「三相、3HP 以下流量最大的是哪款」這類選型問題時，現行檢索只拿得到最相近的幾段型錄，常漏款、排錯、或把額定點和最大值混在一起。

- 知識圖譜擴充沒有幫助：graphify 的節點沒有描述與規格，工業示範專案實測正式與 dev 差不多，純圖譜檢索比向量檢索差（2026-10-05）。
- 產品筆記實驗三輪（`scripts/experiments/product-notes/REPORT.md`）：同一批 20 題、每題 3 次，60 份回答「對／部分對／錯」：
  - 現行檢索 A：9／14／37
  - 加 3 篇最相近筆記 B：14／19／27
  - 加篩選工具 C：55／2／3
  - 直接給全部 15 篇筆記 D：45／10／5

  C 對 D 同題同次 14 勝 41 平 5 敗，贏在漏款、排序與必要限定，篩選工具本身有效。

## 範圍

### 第一階段（這份計畫要做的）

1. 產品規格放在專案知識庫的 `knowledge/products/`：
   - `_catalog.yaml` 定義欄位：名稱、顯示名稱、型別（`number`／`text`／`number_set`）、單位、說明。每個專案自己定，不寫死泵浦欄位。
   - 每個產品一篇 Markdown，YAML frontmatter 放規格值；沒有的值留 `null`，正文照常給檢索用。
   - 停用的文件不列入（跟檢索一致）。
2. Brain 內建工具 `filter_products`：
   - 參數：`scenarios[]`，每個情境有 `name`、`conditions`（AND；運算子 `eq`／`ne`／`lt`／`lte`／`gt`／`gte`／`in`／`contains`）、`sort`（多欄）、`limit`。原本是 `where` 巢狀 `all`／`any` 的 JSON 字串，驗收後改成結構化參數（見「工業示範專案（開發） 驗收」）。
   - 多個需求情境分開放，不合併成 AND（第一輪實驗的錯誤）。
   - 回傳每個情境的 `matches`（符合，含全部規格值與文件路徑）、`unknown`（條件引用的欄位是 null，不能當成不符合）、`excluded_count`。
   - 欄位與運算子對照專案的 `_catalog.yaml` 驗證，錯的回清楚的中文錯誤讓模型改參數。
3. 工具只在有 `_catalog.yaml` 的專案出現，說明裡帶該專案的欄位清單與單位：在 agent loop 組工具清單時處理，跟 fast 模式拿掉上網工具同一個位置。第一輪可以跟 `search_knowledge` 同時呼叫，所以 fast 模式（不准追加工具）也用得到。
4. 測試：篩選語意（null 是未知、多情境、多欄排序、`number_set` 如 `phase: [1, 3]`）、catalog 驗證、工具註冊與依專案隱藏。

### 不做（之後另評估）

- 自動從型錄產生產品筆記：實驗的生成腳本能用，但正文仍有語意錯誤，入庫前要人工核對；第二階段做「生成 → 核對 → 入庫」流程與後台介面。
- 實驗裡的 `operating_point`（額定點候選）：一般化的 `where` 就能表達「額定揚程 ≥ X 且額定流量 ≥ Y」，候選與證實的差別交給回答提示說明，不做泵浦專用邏輯。
- 正式專案的資料：第一階段只把實驗核對過的 15 篇筆記放進工業示範專案（開發） 驗證，正式工業示範專案等使用者確認。

## 驗收

- 單元測試全過，Brain 全套不退步。
- 工業示範專案（開發） 放入 15 篇筆記與 `_catalog.yaml` 後，用實驗第三輪的 20 題經正式聊天路徑（fast 模式）跑一次，對照 C 組 55／2／3。

15 篇筆記與 `_catalog.yaml` 放進工業示範專案（開發） 的 `knowledge/products/` 並重建索引，第三輪 20 題、fast 模式。評分照 `round3/questions.json` 的凍結規則（required_points／forbidden_claims），由獨立的子代理逐份評。

| 版本 | 路徑 | 份數 | 對／部分對／錯 |
|---|---|---|---|
| 已部署的 7c15ec5 | `/api/v1/chat` | 20 題×1 | 5／5／10 |
| 改後（部署前） | 容器內同一套 prompt 與 agent loop | 20 題×3 | 40／15／5 |

已部署版本的問題與改法：

1. 模型很少叫：工具說明寫了「與 search_knowledge 同一輪呼叫」，但系統提示的工具規則只說「search_knowledge 一定要叫」。需要篩選的 16 題，`/api/v1/chat` 20 題只有 7 題叫；容器內 16 題×2 次只有 9 次。改法：有規格表的專案，系統提示多一條規則，要求選型、比較、極值類問題第一輪同時呼叫篩選與檢索，產品清單以 `matches` 為準（`product_prompt_line`）。只加這條：23／32 次。
2. 參數常寫壞：`query` 要模型把巢狀 JSON 寫在字串裡，flash-lite 約三成呼叫被退回（JSON 語法錯、排序寫成 `op` 少了 `direction`、`or` 當鍵）。fast 不准追加工具，退回就沒有第二次機會。改法：參數改成結構化的 `scenarios[]`／`conditions[]`／`sort[]`／`limit`，`field` 用專案欄位做 enum、`op`／`direction` 用 enum，`value` 收字串再依欄位型別轉；巢狀 `all`／`any` 不再對模型開放，同一欄位多選用 `in`，其他 OR 拆情境。改後 48 次呼叫退回 0～1 次，需要篩選的 48 次有 43～45 次拿到篩選結果，不需要篩選的 12 次有 3 次也叫了（無害）。
3. 結果缺數字：`matches` 原本只回條件與排序用到的欄位，模型篩 `hp=3` 卻沒依揚程排序時拿不到揚程，就回「型錄未提及」（Q04 三次全錯）。改法：每列附全部規格（實驗 C 組也是全規格）。這一項把 36／15／9 提到 40／15／5。

試過但拿掉的：fast 第一輪漏叫或被退回時，收工具那輪只留 `filter_products` 讓模型補叫。字串參數時救回 13 次；改成結構化參數後救回 0 次，反而讓模型在那一輪叫 `search_knowledge` 被丟掉、多一輪 LLM，所以拿掉。

部署後經 `/api/v1/chat`：60 次全部 200、沒有空回覆（容器內直接呼叫 agent loop 的 2 次空回覆，正式路徑有備援接住），需要篩選的 48 次有 46 次拿到篩選結果、退回 0 次，耗時中位數 7.2 秒、p90 9.3 秒（含 backend）。錯 4：拿到清單仍說「型錄未提及」1（Q04）、冠軍選錯 1（Q04）、漏款又寫錯功率範圍 1（Q14）、乙現場說查無符合 1（Q16）。部分對 11 多數是缺資料題沒把「因此無法判定」講出來（Q11、Q12、Q19）或沒逐款點名。

跟 C 組還差的地方（容器內 60 份）：

- 錯 5：空回覆 2（`LLMEmptyReplyError`，容器內直接呼叫 agent loop，沒有經過正式路徑的備援；經 `/api/v1/chat` 時會不會變成備援回答待確認）、拿到清單仍回「型錄未記載」2（Q01、Q18 各一次）、漏款又寫錯粒徑 1（Q14）。
- 部分對 15：多數是語音長度限制下省略逐款數字（Q14、Q16 只給範圍），或缺資料題沒有把「因此無法判定」講出來（Q11、Q12、Q19）。C 組的回答沒有語音長度限制，兩者不完全可比。
- 延遲：中位數 4.6 秒、p90 約 6～10 秒（容器內、不含 backend 與 TTS）。

## 正式工業示範專案（2026-10-07）

15 篇筆記與 `_catalog.yaml` 放進正式工業示範專案的 `knowledge/products/`，工業示範專案（開發） 用 `scripts/project_mirror.py sync` 跟著同步。跟實驗的 `round3/notes/` 有兩處不同：

- 50EUB-M-5.20T 額定揚程 15 → 13 m。筆記是對照型錄轉錄稿 `EVAK_CATALOG.md` 驗證的，轉錄稿這一格就抄錯了；改對照型錄原圖（`data/evak_catalog/pages/`）後，其餘 14 篇逐格相符。
- 拿掉正文與 frontmatter 的轉錄稿行號，只留頁碼：轉錄稿更正後行號全部位移。

同一次核對發現轉錄稿有好幾張表跟原圖不符（第 6 頁 EUB、第 17 頁 HIPPO DN、第 20 頁 LEOPARD 整表數字與原圖不同，第 16、18、19 頁電流與重量錯，第 3 頁著脫座），中英西三版與 QA 已依原圖更正。實驗 `round3/` 的筆記與題目保持原樣，作為當時的紀錄。

只放 15 篇時，跨系列的選型題（「3 吋、揚程 20 米以上有哪幾款」）模型只列規格表裡的款式，還說「共 N 款」；系統提示補上規格表範圍後仍補不出其他系列，因為 fast 模式的檢索片段湊不齊各系列的表。所以同一天把規格表擴大到全型錄：第 4～20 頁每張規格表的每一列，口徑二選一的列（`50(80)EUS-5.10`）拆成兩款、材質或 Q 版重量不同的列（`EUBS(I)`、`HIPPO-50(Q)`）拆開，同一列單三相都有的維持一款、`phase: [1, 3]`，原圖沒有的值填 null；共 117 款，每格對過原圖。欄位不變，2 極／4 極與著脫座只寫在正文。

工業示範專案（開發） 經 agent loop（fast）抽測：「3 吋、揚程 20 米以上」12 款全列、「單相、2 吋、揚程 15 米以上」16 款全列、「EUBL 有哪些馬力」與聽錯的「UBL」都答 1 HP（只有 15 篇時答不出或拿 EUB-M 冒充）、「10 匹以上揚程最高」答對；「流量 5000 以上」只講到系列層級。實驗第三輪的 20 題評分規則假設只有 15 款，不能直接拿來評全型錄。

## 風險

- 模型可能不呼叫工具：已實測，只靠工具說明不夠，要系統提示規則加結構化參數（見上）；仍有約一成需要篩選的題目沒叫，必要時之後再加意圖判斷。
- 欄位單位：條件值要先換成 catalog 的單位，說明裡寫明單位與換算提示（例如 1 m³/h = 1000/60 LPM）。

## 工具入口驗證補強（2026-10-12）

既有工具已部署，本次修正接續現有 `filter_products`，沒有另建工具或重寫 QA。發現結構化參數在轉成內部查詢時有三類靜默放寬：舊 `where` 與未知情境欄位被丟棄；`conditions:false`／`sort:false` 等錯誤型別被 `or []` 當成空清單；`limit:false` 被當成不限。前兩類會讓不符合條件的產品列入，或把任意首款當成排序結果。

修正後，頂層／情境額外鍵與舊格式明確報錯，`conditions` 必須明示陣列，`sort` 省略或明示陣列，`limit` 在正規化前排除布林與其他非數值型別；保留 `1.0` 與 `0` 的既有供應商相容行為。合法查詢的符合／未知／排除語意與多欄排序不變，錯誤不會產生放寬後的候選清單。

工具入口新增 21 個回歸案例；其中 19 個在修正前失敗，修正後與既有測試合計 39 個通過。另以既有 API 容器的隔離程序載入修正模組並使用暫存測試資料，39 個通過；沒有替換容器 `/app` 程式或修改 `/data`。

在 API image 內重跑工具入口與每輪決策測試，53 個全部通過；先前在另一個環境看到的 `test_turn_decision_settings_validate_thresholds_and_map_feature_groups` 失敗沒有重現。

本次只改 Brain 工具入口及其測試，工具名稱、已宣告的 JSON 參數形狀、回傳契約與既有錯誤通道保持相同；QA 檢索、Backend、前台／管理介面、SDK 及 protocol contracts 不需修改。計畫狀態仍維持 Draft，沒有以局部驗證代替整體驗收。

入口補強開始時，`project_mirror.py check` 發現 dev 與正式專案的 `.doc_meta.json` 不一致，因此先沒有重新量測。接著唯讀核對確認是 99 筆自動語言快取差異；只按實際解析器補算缺少的 `language/language_source`，完整 129 筆 metadata 相同，知識資料相同，沒有丟棄其他鍵。原始 check 前後仍是 exit 1，沒有 sync、reindex 或寫回 metadata。既有 15 款的凍結題目不套用到現在 117 款全型錄，後續改用下方新題與新標準。
